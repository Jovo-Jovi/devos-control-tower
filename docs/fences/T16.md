### Prompt (canonical)

Link requests from DEV_OS projects arrive in `link_requests` (T15; the route that writes them is T17). Give the owner a
**"Link requests" panel on `/`**, under the overview. It lists every request in three groups:
- **Pending**, with Approve · Decline · Export · Delete;
- **Linked by request**, with Decline (which disconnects the project) · Export · Delete;
- **Declined**, with Export · Delete.

Every change goes through T15's functions with the service-role client, and only after `requireOwner()`. Nothing else
in the Tower changes:
- no route (`src/app/_link-requests` is a private folder, not a segment);
- no migration, no dependency, no header, no host;
- the disconnected state on the map, the list and the project page is T18's.

Rules that hold throughout:
- **The owner only.** The panel is read through the owner's session under RLS on the server render. Each action calls
  `await requireOwner()` as its first statement.
- **No detail leaks (T15 carry-forward (c)).** Any database error, unexpected answer or throw becomes the one generic
  catalogue message `linkRequests.failed`. No error text, code, repository or key is logged, returned or shown from an
  error, and no `console.*` is used in these files.
- **Delete says what goes.** For a request with a project, linked or disconnected, the confirmation says that the
  project and every run and step event go with it. This holds even if the owner created that project.
- **Export stores nothing.** The browser builds the JSON file from the action's answer and downloads it; nothing is
  written to the server's disk or to browser storage.
- **Design.** No colour, px, duration or easing outside `tokens.css`; logical properties only; no `style` prop; no
  literal UI text in TSX (every string from the catalogue); only `transform` and `opacity` animate; the repository and
  every key in `<bdi>`.

### Stage 1 — The server side (proves D6, D7 and D8; D2 with 21 files)

- **S1 — Grouping helper `src/lib/link-requests/groups.ts`** (pure; no `server-only`):
  - `export type LinkRequestState = "pending" | "approved" | "declined";`
  - `export type LinkRequestView = { id; repository; ownerGithubId; proposedKey; engineVersion; contractVersion;
    state: LinkRequestState; projectKey: string | null; firstRequestedAt; lastRequestedAt; decidedAt: string | null }`.
    Every other field is a `string`, and the timestamps are ISO strings.
  - `export type LinkRequestGroups = { pending: LinkRequestView[]; linked: LinkRequestView[]; declined: LinkRequestView[] }`.
  - `export function groupLinkRequests(rows: readonly LinkRequestView[]): LinkRequestGroups`. Pending holds `pending`
    rows, newest `lastRequestedAt` first. Linked holds `approved` rows, and Declined holds `declined` rows; both are
    newest `decidedAt` first. Ties go by `id` ascending. The input is not mutated.
- **S2 — Server module `src/lib/supabase/server/link-requests.ts`** (`import "server-only"`):
  - `readLinkRequests(): Promise<LinkRequestView[] | "unavailable">`. Through `createSessionClient()`, select every
    `link_requests` row with the §2.10 columns and its project's `key` (the `project_id` relationship). Map each row to
    `LinkRequestView`. A query error, or a row with an unknown `state`, gives `"unavailable"`.
  - `export type LinkOutcome = { kind: "approved"; key: string } | { kind: "declined" } | { kind: "deleted"; projectDeleted: boolean } | { kind: "exported"; document: Json } | { kind: "repo_taken" } | { kind: "not_pending" } | { kind: "not_found" } | { kind: "failed" }`.
    `Json` is from `@/lib/supabase/database.types`.
  - `export function linkOutcome(action: "approve" | "decline" | "delete" | "export", response: { data: unknown; error: unknown }): LinkOutcome`
    is pure. It gives `failed` when `error` is not null, when `data` is not a plain object, or for any `result` that
    `action` does not allow:
    - approve: `approved` (only with a `key` matching `^[A-Z][A-Z0-9_-]{1,31}$`), `repo_taken`, `not_pending`, `not_found`;
    - decline: `declined`, `not_pending`, `not_found`;
    - delete: `deleted` (only with a boolean `project_deleted`, kept as `projectDeleted`), `not_found`;
    - export: `exported`, whose `document` is the object without its `result` field, and `not_found`.
  - `approveLinkRequest(id)`, `declineLinkRequest(id)`, `deleteLinkRequest(id)` and `exportLinkRequest(id)` each call
    the matching T15 function through `createAdminClient().rpc(…, { p_request: id })` inside `try`/`catch`. They return
    `linkOutcome(…)`, and `{ kind: "failed" }` on a throw. Nothing is logged.
- **S3 — Server actions `src/app/_link-requests/actions.ts`** (`"use server"`):
  - `approveLinkRequestAction`, `declineLinkRequestAction`, `deleteLinkRequestAction` and `exportLinkRequestAction`
    each take `(id: string)` and return `Promise<LinkOutcome>`.
  - Each body starts with `await requireOwner();`. An `id` that does not match
    `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$` returns `{ kind: "not_found" }` without a call.
  - Otherwise each calls its S2 function. For every outcome except `failed`, and except from export, it then calls
    `revalidatePath("/")`.
  - The file imports nothing from `admin.ts` or `session.ts` except `requireOwner`.
- **S4 — Unit tests.**
  - `groups.test.ts`: (a) three groups and their orders, with ties by id; (b) a declined row with a `projectKey` stays
    in Declined and keeps its key; (c) no rows gives three empty groups; the input array is unchanged.
  - `link-requests.test.ts` follows `import.test.ts`: `vi.mock("server-only", () => ({}))`, the local stack, the admin
    client for fixtures. It uses synthetic requests `fixture-ut/alpha` (`LINKUT-ALPHA`), `fixture-ut/bravo`
    (`LINKUT-BRAVO`) and `fixture-ut/taken` (`LINKUT-TAKEN`), owner `800001`, and a project `fixture-ut/taken` of owner
    `800099` with the key `LINKUT-OTHER`. It removes all of them in `afterAll`. It proves:
    - `linkOutcome`: an error, `null`, an array, an unknown `result`, `approved` with a bad key, and `deleted` without
      a boolean each give `failed`, and the outcome has no field but `kind`;
    - approve → `approved` with the proposed key, then `not_pending`; the taken repository → `repo_taken`; a random
      uuid → `not_found`;
    - decline → `declined`;
    - export → `exported`, with `document.request.repository` right and no `result` field;
    - delete of the approved request → `deleted` with `projectDeleted: true`, and the project is gone.

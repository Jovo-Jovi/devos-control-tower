### Prompt (canonical)

Link requests from DEV_OS projects arrive in `link_requests` (T15; the route that writes them is T17). The owner has a
**"Link requests" panel on `/`**, under the overview. It lists every request in three groups:
- **Pending**, with Approve · Decline · Export · Delete;
- **Linked by request**, with Decline (which disconnects the project) · Export · Delete;
- **Declined**, with Export · Delete.

Every change goes through T15's functions with the service-role client, and only after `requireOwner()`. Nothing else
in the Tower changes:
- no route (`src/app/_link-requests` is a private folder, not a segment);
- no migration, no dependency, no header, no host;
- the disconnected state on the map, the list and the project page is T18's.

Rules that hold throughout:
- **The owner only.** The panel is read through the owner's session under RLS on the server render. Each action calls
  `await requireOwner()` as its first statement.
- **No detail leaks.** Any database error, unexpected answer or throw becomes the one catalogue message
  `linkRequests.failed`. No error text, code, repository or key is logged, returned or shown from an error. These files
  use no `console.*`.
- **Delete says what goes.** For a request with a project, linked or disconnected, the confirmation says that the
  project and every run and step event go with it.
- **Export stores nothing.** The browser builds the JSON file from the action's answer and downloads it.
- **Design.** No colour, px, duration or easing outside `tokens.css`; logical properties only; no `style` prop; no
  literal UI text in TSX; only `transform` and `opacity` animate; the repository and every key in `<bdi>`.
